# RoomCraft AI — аудит и первый этап

Дата: 18 октября 2026. Объём: существующий Flutter MVP, Node.js backend, конфигурация Firebase, публичная страница. Production-настройки и данные не изменялись.

## Устройство проекта

- `lib/app.dart`: MaterialApp, именованные маршруты `/`, `/login`, `/mode`, `/ai_create`, `/result`, `/editor`. Часть переходов использует MaterialPageRoute. Состояние локальное: StatefulWidget, setState, аргументы маршрутов; отдельного общего слоя состояния нет.
- Firebase инициализируется перед runApp. Ошибка инициализации пока оставляет приложение без пользовательского экрана ошибки. Linux не настроен в firebase_options.dart.
- Вход/регистрация: Firebase email/password; после входа открывается выбор режима. Профиль содержит выход. Есть гостевой путь; AI ограничен зарегистрированными пользователями на стороне Flutter.
- AI: multipart POST с фото, style, prompt и userId. Ответ с imageUrl открывается на экране результата. В текущем коде один запрос и один результат, а не три варианта. Отсутствуют timeout, ограничения размера и проверка содержимого фотографии.
- Backend: Express, multer, Firebase Admin, Replicate FLUX Kontext Pro; отдельная модель удаления фона. Загрузка и результаты находятся на локальном диске сервера.
- Редактор: ручное размещение, масштабирование и вращение предметов, собственные изображения и удаление фона; данные передаются в результат. Это не редактор AI-масок. Повторная генерация через существующий AI-экран не составляет дерево версий.
- Сохранение: `users/{uid}/savedWorks`, серверная дата, URL, base64-превью и JSON размещённых предметов. Загрузка списка/stream, повторное открытие и удаление реализованы в коде. Надёжность сохранения и авторизация требуют проверки с реальным аккаунтом.
- CustomItemsService хранит предметы в SharedPreferences под общим ключом устройства, без разделения пользователей. Это потенциальное смешение личных данных при смене аккаунта.
- `lib/theme` и часть файлов widgets первоначально пустые. Стили повторяются inline. Редактор — более 1200 строк с UI, запросами и состоянием вместе.
- Android, iOS, macOS, Linux, Windows, Web scaffold присутствует. До этого изменения тестов в репозитории не было.

## Приоритетные проблемы

1. **Авторизация backend.** userId берётся из body, Firebase ID token не проверяется. `/remove-background` вообще не требует пользователя. Клиентская проверка не защищает платные операции.
2. **Расходы API.** Счётчик aiGenerations не является лимитом; чтение/увеличение не атомарно. Нужны rate limit, квоты с транзакцией резервирования и контроль размера загрузок.
3. **Правила Firebase.** Файлов Firestore/Storage rules в репозитории нет. Путь по uid сам по себе не гарантирует изоляцию. Опубликованные правила не прочитаны и не изменены.
4. **Хранение.** `/generated` публичен, файлы живут на диске хостинга; долговечность URL не гарантирована. Нужен приватный Storage с проверенной политикой доступа. Base64 в Firestore ограничен размером документа; новая схема требует плана миграции.
5. **API-конфигурация.** Генератор обращается к Render, редактор по умолчанию к localhost:3000; Railway указан как альтернативный адрес. Нужен единый конфиг окружения.
6. **Prompt.** Сервер навязывает минимальное точечное редактирование, запрещая полный redesign; это конфликтует со сценарием создания интерьерной концепции. Разделить generation/edit задачи перед изменением prompt.
7. **Надёжность backend.** Нет лимита multer, проверки MIME/содержимого, гарантированной очистки при раннем ответе, проверки статуса скачивания результата. req.body логируется целиком. Не внедрять в пилот без исправления.
8. **UX.** Удаление работы без подтверждения; ошибки stream могут выглядеть как пустой список; stream создаётся во время build. Полноценные проекты, клиентские поля, версии, статусы и история пока отсутствуют.
9. **Производительность.** Списки работ строятся полностью через Wrap, превью и base64 могут занимать много памяти. В результате изображение захватывается с pixelRatio 3; кодирование thumbnail синхронное. Нужна пагинация и перенос тяжёлой обработки отдельно от UI.

Проверка кода не равна подтверждению работоспособности Firebase/Replicate. Сервисный аккаунт и REPLICATE_API_TOKEN не предоставлены в репозитории. Платные запросы и записи production не выполнялись.

## Реализовано в этом этапе

- Заполнены токены цвета, типографики и Material Theme. Тёплые ivory/sand/charcoal, локальный Lora с кириллицей и OFL-лицензией.
- Вместо стартовой заглушки — публичная адаптивная страница: hero, ориентиры стилей, четыре шага, блок для студий, финальный CTA и footer.
- Сохранены имя SplashScreen и маршрут `/` для обратной совместимости. CTA ведут на существующий `/login`; навигация по секциям с учётом системного уменьшения анимаций.
- Изображения локальные, не требуют внешних запросов при открытии страницы; разрешение декодирования ограничено. Галерея помечена как интерьерная фотография, не выдаётся за генерации или выполненные студией проекты.
- Устранены замечания анализатора без изменения схемы данных: withValues, проверка mounted, ненужные imports. Числовые имена прежних экранов сохранены с локальным исключением file_names.
- Динамические IconData заменены разрешением сохранённых codePoint через каталог констант: release tree shaking сохраняется; неизвестный старый значок отображается как category. Сохранённые данные не переписываются.
- SDK Flutter 3.47.5 обновил четыре транзитивных SDK/test зависимости в lockfile; прямые зависимости и технологический стек не менялись. SDK также добавил стандартные исключения платформенных build-каталогов в analysis_options.yaml.

## План следующих этапов — до крупных изменений

1. Закрыть авторизацию и квоты backend совместно с обновлением Flutter-клиента. Объединить API-конфиг. Проверить правила Firestore на эмуляторе; production только после отдельного согласования.
2. Ввести ProjectRepository и модель проекта в отдельной коллекции, сохранив чтение legacy savedWorks. Добавить dashboard и мастер проекта. Согласовать миграцию и приватное файловое хранилище до переноса данных.
3. Выделить GenerationService, состояния ожидания/выполнения/ошибки и реальные независимые задания для 1–3 вариантов с ограничением параллелизма и расходов.
4. Добавить версии результатов с parentVersionId, выбором и возвратом версии. AI-редактирование отделить от ручных overlays. Маски — только после выбора и проверки отдельной модели/API.
5. Пагинация проектов, интеграционные тесты авторизации/квот/сохранения и пилот с тестовым аккаунтом студии.

Будущие workspaceId, роли, согласования и PDF следует вводить через сервисные интерфейсы и явную схему доступа, а не добавлять неработающие кнопки. На этом этапе эти функции не заявлены реализованными.

## Ручная проверка перед демонстрацией

- Chrome/Safari, клавиатура, 200% масштаб, большой системный текст, мобильный touch и reduced motion.
- Вход/регистрация тестового пользователя, выход и повторное открытие старой сохранённой работы.
- Один разрешённый платный запрос к AI с тестовой фотографией: успех, отказ API, таймаут; затем сохранение и повторное открытие.
- Правила изоляции двух пользователей, размер сохраняемых данных, доступность URL после перезапуска backend.
- Android/iOS сборки и сохранение в галерею на физических устройствах — не проверены в текущем этапе.
